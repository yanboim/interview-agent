# 测试策略

## 目标

验证业务行为、数据隔离、并发正确性、部署兼容和AI质量，并让失败尽可能靠近变更
发生的位置。

## 测试层级

| 层级 | 重点 | 示例 |
|---|---|---|
| 纯单元 | 计算、解析、状态规则 | 学习、能力、分块、评估 |
| 应用服务 | 用例、幂等、失败恢复 | 聊天和面试生命周期 |
| 存储/迁移 | 事务、约束、历史升级 | SQLite、Alembic、PostgreSQL |
| API契约 | 身份、状态码、DTO、Header | Auth、Admin、Chat、Interview |
| 前端单元 | API解析、Store和组件 | NDJSON、Markdown、观测 |
| 浏览器E2E | 关键旅程、移动端、可访问性 | 登录、目标、聊天、面试 |
| AI评估 | 检索、路由、引用、忠实度 | `eval/` 数据集与报告 |
| 运行验证 | 健康、迁移、发布、回滚 | Compose/Canary检查 |

## 核心测试原则

- 用户数据功能包含第二用户的越权负向测试；
- 幂等和并发功能包含同键、不同键、不同正文和所有者令牌测试；
- Migration测试历史数据回填，而不只验证新空表；
- 外部模型默认用可控替身；Live评估显式且记录成本和数据审批；
- Qdrant测试不删除或替换正在服务的集合；
- E2E覆盖桌面、移动、键盘、错误和恢复，不只验证页面出现。

## 环境

- 默认后端测试使用隔离SQLite；
- PostgreSQL特性使用 `TEST_POSTGRES_URL`；
- Redis集成测试使用明确测试实例；
- Playwright使用隔离数据库和Worktree端口；
- Live模型/RAG测试只有在任务要求、凭据配置且数据允许外发时运行。

## 缺陷处理

缺陷先补能复现问题的测试，再修复。重复出现的边界问题登记技术债；生产事故还需要
运行手册和复盘更新。
