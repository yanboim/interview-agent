# 持久聊天回合生命周期

## 上下文

原聊天路径在调用模型前持久化用户消息，只在成功后持久化助手消息。失败和客户端断连
会留下孤立用户消息；并发请求可能读取同一历史并同时调用模型，产生不确定顺序。

## 决策

增加 `chat_turns` 作为命令/流程记录。回合包含：

- 持久 `turn_id` 和会话内 `turn_index`；
- 客户端 `idempotency_key` 以及请求摘要/内容；
- `pending`、`generating`、`completed`、`failed` 或 `cancelled` 状态；
- 领取所有者Token、部分/最终助手内容、元数据、错误和时间戳。

每个会话保存 `next_chat_turn_index` 和 `active_chat_turn_id`。开始命令时，仅在活动回合
为空时条件设置它，并在同一事务中递增序号。这会跨应用副本串行化同一会话的模型调用，
不依赖Python锁。

新回合在事务提交前从 `pending` 转为 `generating`。成功时，所属领取变为
`completed`，用户和助手消息一起插入，活动槽在同一事务中释放。失败和取消回合保留，
但不出现在消息历史中。

## 重试结果

- 相同已完成Key和内容：重放存储的回答和元数据。
- 相同Key仍在生成：返回可重试冲突。
- 相同failed/cancelled Key和内容：重新领取同一回合和序号。
- 相同Key但内容不同：拒绝幂等键误用。
- 会话生成中使用不同Key：模型调用前拒绝。
- 终态失败后使用新Key：分配下一个逻辑回合。

## 流式断连

服务端把生成器取消与普通异常分别处理，将已累计的部分回答保存为 `cancelled`，释放
会话活动槽，再继续传播取消。重试从头生成；精确延续提供方Token不在本变更范围内。

## 兼容性

遗留完成消息继续可读并作为模型上下文。迁移按遗留用户消息数量加一初始化下一序号，
不会为旧历史合成生命周期行。
