# 回滚运行手册

## 原则

应用、数据库、配置和知识库是不同回滚面。先识别故障面，再执行最小安全回滚；
不要把数据库恢复或集合删除当作一般诊断动作。

## 应用回滚

1. 停止继续发布和迁移。
2. 确认上一已知良好制品的摘要。
3. 评估新版本是否已写入旧版本不能读取的数据。
4. 将应用/Worker切回兼容制品。
5. 验证健康、就绪、核心流程和错误指标。

## 数据库

Alembic downgrade不等于无损回滚。新版本写入数据后，删除列或表可能造成永久丢失。

优先顺序：

1. 保持新Schema并回滚到向前兼容的应用；
2. 发布向前修复；
3. 只有在验证数据影响和维护窗口后执行特定Downgrade；
4. 最后手段才从备份恢复整个数据库。

数据库恢复会覆盖目标数据，必须显式确认并按
[备份恢复手册](../operations/BACKUP-RESTORE.md)执行。

## 知识库

通过管理员状态接口确认目标：

```text
GET  /api/admin/knowledge/status
POST /api/admin/knowledge/rollback
{"collection_name":"<managed-version>"}
```

回滚只移动稳定别名，不删除当前或目标集合。不要手工删除别名当前目标。

## 配置与Secret

配置回滚需要确认旧应用与当前Schema/数据兼容。Secret泄露应执行轮换而不是简单改回
旧值，同时撤销相关Token并审查日志。

## 回滚后

- 记录触发原因、时间、版本、数据影响和验证；
- 保留失败制品和日志供调查；
- 建立事故记录或技术债；
- 明确重新发布前的新增门禁。
