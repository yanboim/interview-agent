# interview-agent 作为 Agent 应用的不足分析(15 条)

已完成只读审查 + 关键代码路径核实。所有结论均经代码验证(引用路径真实存在、行号准确)。**本任务交付物是这份分析本身,不涉及代码改动。**

---

## A. Agent 编排与智能度

**1.【最严重】子 Agent 完全没有对话上下文**
`app/multi_agent.py:155-156` 委派任务时只传 `[HumanMessage(content=task.strip())]`,无历史、无滚动摘要。12K token 预算和摘要只被 Supervisor 消费,真正干活的 knowledge/interviewer/evaluator/planner 全部失忆。"再展开第二点"委派后子 Agent 不知"第二点"指什么。**记忆机制在默认部署下被架空。**

**2. 路由纯自然语言 prompt,无置信度/纠偏/fallback**
`multi_agent.py:22-41` 的 `SUPERVISOR_PROMPT` 用中文关键词列举做路由,无结构化护栏。误路由直接整合输出。且 evaluator_agent `tools=[]`(`multi_agent.py:134-140`)无法多轮澄清,设计断裂。

**3. 无并行执行,延迟结构性叠加**
子 Agent 工具是同步 `invoke`(`multi_agent.py:153`),并发 tool_call 也排队;RAG 内 dense 预筛与 hybrid 检索顺序执行(`tools.py:92-119`)。Supervisor→子Agent 嵌套 ReAct,最坏端到端分钟级。交互式场景硬伤。

**4. 无 Agent 层反思/自检,递归上限未配置**
全仓无 reflection 节点;`chat.py:107/254` 的 ainvoke/astream 未传 `recursion_limit`,沿用默认 25。嵌套调用易触顶抛 RecursionError。

**5. 出题/评分双实现割裂,JSON 解析脆弱**
`interview_engine.py:69/122` 绕过 agent 直调模型,而 interviewer/evaluator agent 又 `tools=[]` 纯 LLM。评分用 `re.compile(r"\{.*\}", re.DOTALL)`(`interview_engine.py:11`)贪婪匹配,多 JSON 块即抓错,无 `with_structured_output`。

## B. RAG 质量

**6. 完全无查询改写/HyDE/multi-query**
全仓搜 `multi_query|HyDE|query_rewrite` 零命中。原始 query 直接 embedding(`tools.py:97-98`)。口语化短问面对长篇技术文档召回率低。

**7. dense 门控 k=1 + 0.4 阈值,脆且绕过重试**
`tools.py:99` 取最近 1 条 dense 邻居,`tools.py:104` 比阈值,top-1 略偏即 `return`"无资料"。early return 退出整个函数而非循环——Qdrant 抖动让重试白写。

**8. 无内容级去重 + 主题无关分块**
`tools.py` 无 dedup;10 个近似"1000 面试点"大文件的近重复 chunk 占掉最终槽位。`chunking.py` 无主题 metadata,查询无法按 Java/Go 过滤。

**9. 引用来源暴露文件系统路径**
`ingest.py:42` `metadata={"source": str(file_path)}`,`tools.py:193` 原样吐给 LLM。模型/用户看到裸路径,难看且泄露部署结构。

## C. 记忆与上下文

**10. token 估算用字节长度,中文过估 2-3 倍**
`chat_context.py:30-32` `estimate_text_tokens = len(text.encode("utf-8"))`。中文 1 字=3 字节约 1-2 token,12000 预算实际只放 4000-6000 真实 token。过早触发摘要,且每条裁到 240 字节(`chat_context.py:53`),代码/详细答案信息损失大。

**11. 失败/取消轮也推进摘要基线**
`storage.py:562-580` 摘要写回耦合在 turn-claim 事务。claim 成功但 Agent 失败时,旧消息已折叠进摘要,下轮记忆基线漂移。

## D. 可观测性

**12. OTel span 不覆盖 Agent 链路,关键指标缺失**
`telemetry.py:33-34` 只 instrument FastAPI+SQLAlchemy,无 redis/httpx/langchain,无手工 span 包裹"路由→检索→工具→LLM"。Prometheus(`operations.py:78-111`)无 LLM 延迟直方图(只有累计值,算不出 p50/p95)、无单工具成功率。

## E. 安全与韧性

**13. 无输入护栏/输出过滤**
`app/api/schemas.py:11-14` 只长度校验;流式(`chat.py` token 事件)直吐 LLM 原文。可注入"泄露 system prompt",无幻觉/事实校验(只靠 prompt 软约束)。

**14. 错误透传内部异常,流式无端到端超时**
`chat.py:179`、`:367` 把 `f"Agent 执行失败:{exc}"` 直返客户端,绕过 `model_gateway.py:28-33` 脱敏,可能暴露路径/SQL。ainvoke/astream 外层无 `asyncio.wait_for`,Supervisor 反复路由时墙钟无上界。

## F. 成本与测试

**15. token 成本追踪名存实亡,限流对流式无意义**
`multi_agent.py:92-106` 的 record_* 函数是死代码(全仓无调用方);无 per-user 配额、无美元折算、无请求级熔断。限流按 IP 固定窗口(`main.py:224-233`)而非按用户,对流式长连接无效。eval 极薄:routing 16 条、answer_quality 3 条,无 injection/幻觉/配额回归。
